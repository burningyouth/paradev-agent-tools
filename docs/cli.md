# CLI для расширений и автоматизации

`paradev-agent` убирает ручную рутину вокруг сессий Codex и Claude Code в [Superset](https://docs.superset.sh/cli),
коммитов и worktree-слотов: каждая операция — одна команда с проверками, `--json` и
понятными кодами выхода вместо чтения экрана терминала.

- `paradev-agent` — сессии Codex/Claude: список, создание, отправка с подтверждением, ожидание маркера **по журналу**,
  закрытие с сохранением и `resume`, алиасы.
- `paradev-agent commit` — коммиты по плану JSON: сухой прогон на временном индексе, затем `--apply`.
- `paradev-agent slot` — worktree-слоты проекта: состояние, создание нового слота, подготовка под новую ветку от
  свежего `origin/<base>` с бэкапом, перенос локальных (исключённых из Git) файлов между слотом и основной копией.

CLI написан на Go и поставляется готовым исполняемым файлом. `git push` CLI не делает никогда.
Правила работы с репозиторием описаны в [AGENTS.md](../AGENTS.md).

## Установка

Из чата используйте [Paradev Agent Tools](../README.md). Самостоятельный CLI работает из терминала с локальным хостом Paradev и подходит для скриптов и локальных расширений.

```sh
"$HOME/.codex/plugins/paradev-agent-tools/launch" --agent-cli install
export PATH="$HOME/.local/bin:$PATH"
paradev-agent --help
```

`install` создаёт ссылку `~/.local/bin/paradev-agent` на бинарник для этой платформы. При обновлении ссылки от прежней версии установщик сохраняет её копию. Выберите другой каталог через `--directory` или проверьте план через `--dry-run`. Для сборки из исходников выполните `go install ./cmd/paradev-agent`.

Для настройки скиллов, хуков и проверки зависимостей есть отдельные команды. [Настройка исполнителей](skills.md#подключение)

## Обычный путь работы

| Что нужно | Команда |
| --- | --- |
| Понять текущий контекст | `paradev-agent status` |
| Выделить слот исполнителю | `paradev-agent slot take --project P --branch B --task KEY` |
| Запустить исполнителя в нём | `paradev-agent create --workspace W --branch B --task KEY --prompt-file task.md` |
| Передать уточнение / получить ответ | `paradev-agent send` / `wait` / `last` |
| Завершить собственную задачу и освободить слот | `paradev-agent close --summary-file outcome.md` |
| Закрыть сессию и освободить все её слоты | `paradev-agent close <UUID> --workspace W` |
| Убрать старые сессии | `paradev-agent gc` — сначала план, затем `--apply` |

`slot take` сам выбирает свободный слот, создаёт его при необходимости и готовит ветку.
`slot create` и `slot prepare` нужны для отдельных операций управления слотами; повторять их после take не нужно.
При продолжении работы в уже открытом слоте его подготовка описана в [agent-slots](../skills/agent-slots/SKILL.md).
Слоты и `create` — только для отдельных задач, порученных пользователем или оркестратором.
Независимое ревью и проверку своей работы выполняет встроенный субагент в той же рабочей копии:
он видит настоящий `git diff` с незакоммиченными правками. Новый слот, `create` и ветка-копия
для этого не нужны; повторное ревью передавай тому же субагенту.
Отдельная сессия для ревью — только по прямой просьбе человека.
При делегировании отдельной задачи подготовку и запуск выполняет оркестратор: `create --workspace W --branch B --task KEY --prompt-file F`.
Чистый свободный слот можно переиспользовать при открытом idle-чате, если за ним нет
активного назначения или живого транспорта. После переназначения этот чат не получает допуск к новой ветке.
Лимит считают по уникальным терминалам Paradev с подтверждённой работой. Если чат и CLI видны в одном терминале, наличие работы в любой строке занимает одно место. `ls` показывает отдельно работающие, ожидающие решения, открытые без работы и неизвестные терминалы.
Create отказывает в грязном, неподготовленном или занятом слоте, сверяет ожидаемую ветку/задачу и
передаёт стартовый self-check. Исполнитель проверяет назначение и не создаёт себе другой слот.
Сессия остаётся в рабочей копии запуска: main — в main, слот — в этом слоте. Workspace main и
Git-ветка main/master — разные вещи: ветку задачи в основной копии готовят по правилам проекта.
При `slot: null` роутер не предписывает брать слот или переходить в другой worktree.
Для вручную открытого чата в слоте проверку и подготовку текущего слота выполняет сам этот чат по личному роутеру.
Наличие установленного скилла не гарантирует его выбор: личный always-on вход в Codex задаётся
в пользовательском `~/.codex/AGENTS.md` (или активном override), не в командных файлах продукта.


Завершение — одна команда `paradev-agent close`: сохранить историю, закрыть сессию, выполнить release
и проверить, что слот действительно свободен. Грязная копия, чужая сессия или ошибка release —
блокер, а не успешное завершение. Ветка задачи сохраняется для `paradev-agent resume`.
`finish`, `slot release` и префикс `sess` поддерживаются только для совместимости старых вызовов.

Краткая справка: `paradev-agent --help`. Подробности: `paradev-agent resume --help`, `paradev-agent slot --help`;
по команде: `paradev-agent close --help`. [Полный справочник команд](commands.md) включает
служебные операции: алиасы, keep, forget, ручной sync и установку скиллов.
У всех команд есть `--json`; ошибки в нём — `{error, code}`.

### Коды выхода

| Код | Значение |
| --- | --- |
| 0 | успех (в `wait` — маркер найден, без `--marker` — ход закончен) |
| 1 | ошибка |
| 2 | таймаут |
| 3 | сессия ждёт разрешения или ответа на вопрос — вид и текст с экрана в выводе `wait`/`last` (`send` в таком состоянии отказывает без `--force`) |
| 4 | ход закончен, маркера нет — вопрос, простой или забыл маркер |
| 5 | ошибка API в журнале |
| 6 | живой сессии в терминале нет |
| 7 | `send`: нет подтверждения за `--timeout` (или завис вызов superset) — сообщение **могло дойти**, не отправляйте повторно вслепую: `last` / `wait` без `--after` |
| 8 | `create`/`resume`/возобновление через `send`: достигнут лимит сессий |
| 9 | проверка не пройдена (`commit`, грязный слот) |

### Команды в текущем контексте

```sh
paradev-agent status                 # проект, слот, фактическая ветка, изменения, сессии
paradev-agent last              # последний ответ текущей сессии
paradev-agent slot sync-back         # план переноса локальных файлов в основную копию
paradev-agent slot sync-back --apply # применить перенос
paradev-agent slot sync --apply      # синхронизация в обе стороны
paradev-agent close                  # закрыть сессию и освободить текущий слот
```

`sync-back` и `sync` без имени выбирают текущий слот: точный
`SUPERSET_WORKSPACE_ID`, иначе cwd (включая подкаталоги и пути через символические ссылки).
При неоднозначности или устаревшем ID — отказ, имя/ID слота можно указать явно.
Основная копия не подставляется вместо слота. Явный `--project` должен совпадать с проектом
текущего слота. У синхронизации без `--apply` остаётся сухой прогон, конфликты дают код 9.

`status` читает состояние проекта и сохраняет обнаруженные сессии в локальную историю. Ветку, HEAD и список изменений берёт из Git выбранного workspace,
а не из колонки Superset; staged, unstaged и untracked различаются кодами Git. При нескольких
сессиях показывает все; текущую отмечает, если её можно определить однозначно. JSON содержит
`project`, `workspace`, `slot`, `git`, `session`, `selection` и `sessions`.
`selection`: `selected`, `ambiguous`, `unmatched` (сессия из окружения не найдена) или `none`.
Переписку status не читает. Вне зарегистрированных workspace показывает Git текущего каталога;
ошибки связи с Superset не маскируются. Работает также в основной копии и в detached HEAD.

```sh
paradev-agent close --note "готово"          # из терминала слота, без поиска ID/алиаса
paradev-agent close --force --note "готово"  # агент закрывает свою работающую сессию по поручению человека
```

Без аргумента `close` и `last` сначала ищут Codex по `CODEX_THREAD_ID` (в том числе нативному ID chat),
затем сессию своего `SUPERSET_TERMINAL_ID`. Из отдельного терминала выбирается единственная живая
сессия `SUPERSET_WORKSPACE_ID`; вне Superset workspace определяется по cwd, включая подкаталоги.
Несколько сессий — отказ с просьбой указать ID/алиас. Закрытая история chat не участвует в выборе.
Устаревший thread/workspace ID не разрешает переключиться на соседнюю сессию.

При закрытии собственной сессии CLI возвращает `status: queued` с `resultFile`.
Код 0 подтверждает запуск worker, а не освобождение слота. Только `status: completed`
означает проверенное завершение; результат читается через `paradev-agent close --result F`.
Для собственного chat в слоте worker сначала ждёт подтверждённого финального ответа с receipt
(см. [close](#close-закрыть-сессию-и-освободить-слот)). Терминальное самозакрытие дожидается выхода
вызывающего CLI. Без живой сессии `paradev-agent close` из слота завершает его release; можно явно указать `--workspace W`.
В основной копии, где слота нет, закрывается только сессия: `release.status: not-applicable`.

## Запуск задачи в слоте

Для скрипта с известными проектом и веткой можно опустить `--workspace`:

```sh
paradev-agent create --project P --branch B --task KEY --prompt-file F --json
```

CLI берёт первый свободный слот по номеру, выполняет стандартный prepare и запускает сессию.
При явном `--workspace` проверяет назначенный workspace, включая main.
Для уже подготовленного слота достаточно одного `create --workspace W --branch B --task KEY --prompt-file F`.
Проверки занятости, состояния Git и назначения слота выполняются при запуске под блокировкой.
При подтверждённом запуске используйте ID из ответа. Status нужен при ошибке, неоднозначном результате
или устаревшем назначении.
Если свободных слотов нет, интерактивная команда первым сообщением спрашивает разрешение создать новый.
Любой ответ кроме `да` или `yes` отменяет запуск. Для скрипта код 3 и JSON
`status: confirmation_required` возвращают `question`. Покажи этот вопрос пользователю и только после
согласия повтори ту же команду с `--allow-create`. Повтор сначала проверит свободные слоты заново.
До согласия задача остаётся в исходном файле, рабочая сессия ещё не запущена.
Самостоятельная команда управления слотами `slot take` сохраняет прежний договор: она может создать слот.

### Резерв и освобождение в Paradev Host Service

Собранный с поддержкой жизненного цикла хост управляет слотами для всех адаптеров чата.
Хост принимает локальную команду из `state/chat-slots.json` каталога данных Paradev
(обычно `~/.paradev`). Пример конфигурации:

```json
{
  "command": "/absolute/path/to/paradev-agent-tools/launch",
  "args": ["--agent-cli"]
}
```

Хост резервирует выбранный свободный `slot-N` при открытии чата и передаёт первое сообщение
модели в исходном виде. Правила проекта определяют, нужны ли задача и ветка для дальнейшей
работы. Хост не извлекает назначение из текста сообщения. Чтобы явно подготовить новый слот
и запустить в нём агента, используй `paradev-agent create --project P …`.

С первым сообщением слот обычного чата получает имя `slot-N · чат`, даже если ветки задачи
ещё нет. Когда тема поручения понятна, агент даёт слоту имя `slot-N — <тема>` через
`paradev-agent slot title --title "<тема>"` или MCP `chat_title`. Ветка и задача проекта
сохраняются. У вручную открытого чата можно выставить подпись с точными ID workspace и сессии,
даже если резерв хоста не включён. При штатном освобождении возвращается имя `slot-N`.

Чат в слоте запускается после проверки рабочей копии и отсутствия других сессий.
Для занятого слота хост показывает причину. После штатного освобождения старой ветки
в слоте можно открыть новый чат.

Закрытие чата освобождает чистый слот после остановки процесса. Git переходит в detached HEAD
на доступной локально базе, имя возвращается к `slot-N`, прежняя ветка сохраняется. Перед
подготовкой следующей ветки CLI обновит базу через fetch. Чтобы завершить **задачу** и
оставить **чат** открытым, закончи проектный процесс и вызови из рабочего слота:

```sh
paradev-agent task complete CHAT_ID --workspace WORKSPACE_ID --json
```

В MCP используй `task_complete` с точными ID. Вызывай перед финальным ответом, после всех
необходимых проверок, коммитов и мержа по правилам проекта. Хост проверяет явный запрос после
завершения хода и фоновой работы. Обычный коммит, push или merge ничего не освобождает.
После освобождения история остаётся в том же чате. Новое поручение повторно резервирует этот
workspace, если он свободен, и запускает адаптер. Если слот уже занял другой чат, появится вопрос.
Грязная копия, смена HEAD после запроса и чужая сессия блокируют освобождение.

### Резервный хук для старых версий Paradev

На хосте без общей поддержки жизненного цикла доверенный `UserPromptSubmit` проверяет
принадлежность чата рабочей копии. Он сверяет workspace и terminal ID с живой записью Paradev,
а также UUID Codex, если Paradev уже его опубликовал. В свободном слоте первое сообщение
передаётся модели в исходном виде. Ветка, созданная во время работы чата, сохраняется
при освобождении слота. Повторные сообщения своего чата проходят и при его незакоммиченных
изменениях. Если слот принадлежит другой сессии или его нельзя безопасно занять, хук
показывает причину. Для основной копии действуют правила проекта.

Текущий Codex-адаптер Paradev пропускает событие `hook/completed`, где Codex возвращает вопрос.
Чтобы вопрос появился **в чате**, добавь в окружение пресета Codex:

- `PATH` — каталог `bin/<операционная-система>-<архитектура>` этого пакета перед каталогом настоящего Codex, например `bin/darwin-arm64`.
- `AGENT_REAL_CODEX` — абсолютный путь к настоящему исполняемому файлу Codex.

Штатная обёртка Paradev найдёт `codex` в PATH и будет запускать через него реальный Codex.
Ретранслятор передаёт вопрос блокирующего хука как уведомление в том же ходе чата, до его завершения.
Хук также отправляет вопрос уведомлением рабочего пространства и сохраняет его локально
в записи события, если адаптер чата пропустит причину.
Для применения настроек открой новый чат.

## История и восстановление

Для ручного закрытия чата подключи хуки через `paradev-agent hook install --agent codex` или `--agent claude`. Установщик
сохраняет существующие хуки, делает бэкап и не подтверждает доверие за пользователя. В Codex новые
определения нужно проверить и разрешить на экране Hooks need review при запуске `codex` в терминале
(или через `/hooks` внутри него; в чате Superset этой команды нет), затем открыть новую сессию.
В списке они подписаны «agent-cli: регистрация сессии», «agent-cli: сохранение состояния»
и «agent-cli: освобождение слота». Codex также показывает «agent-cli: проверка рабочего слота». Изменение определения может потребовать повторного доверия.
`SessionStart` сохраняет назначение, `Stop` — последний ответ, `SessionEnd` запускает короткоживущий
worker: дождаться фактического завершения, записать закрытие и выполнить обычный проверяемый release.
Для Codex-чата с подтверждённым назначением `SessionEnd` сохраняет текущую ветку и HEAD,
в том числе после переключения на релизную ветку внутри чата. Изменение рабочей копии
после этого снимка блокирует освобождение.
Если у закрытого чата не было назначения, worker может освободить только чистый слот с прежней
влитой веткой, при условии что назначение слота не менялось и других сессий нет.
Результаты — `~/.agent-cli/end-jobs/*.json`, чтение — `paradev-agent close --result F --json`.
Повторный hook и явный close не повторяют освобождение. Dirty/чужая сессия/смена назначения блокируют
release и дают уведомление; ветка и файлы сохраняются. Конец ответа, clear и события субагента слот не освобождают.
При аварийном выходе hook может не прийти; восстановление остаётся через log/resume и обычный close.
Доставка SessionEnd кнопкой закрытия конкретного клиента зависит от его интеграции с агентом.

```sh
paradev-agent log --project P --task KEY
paradev-agent resume task-x
paradev-agent resume --task KEY --project P
paradev-agent resume --last-closed --project P
paradev-agent resume --all-open --project P --dry-run
```

Журнал сохраняется автоматически при create, resume, обнаружении через ls/status/last и до закрытия.
В нём — алиас, агент и chat/cli, полные UUID Superset и провайдера, terminal/workspace/путь/проект,
Git-ветка и HEAD, задача, известные параметры запуска, заметка, время и причина закрытия.
Запрос закрытия, подтверждённое закрытие и ошибка — разные события. Новые UUID связаны с прежними.
`log` читает локальный журнал без Superset; `--json` возвращает снимки `sessions` и события `events`.
Старые записи читаются без обязательной миграции; неизвестные поля не угадываются.

У resume ровно один селектор: алиас/UUID, --task, --last-closed или --all-open. При неоднозначности
CLI показывает UUID для выбора. --all-open возвращает записанные открытыми сессии, которых сейчас нет
среди живых; закрытые доступны по алиасу/UUID и --last-closed. --project ограничивает поиск.
Уже живую сессию resume повторно не запускает. Лимит 5 общий для Codex/Claude и chat/cli;
запуски CLI сериализуются, --force лимит не обходит. Пакетное восстановление последовательное,
по каждой сессии возвращается результат или блокер, автоматически закрывать другие сессии оно не будет.

Resume сохраняет агент и транспорт, проверяет workspace, репозиторий, ветку, задачу и занятость.
Грязную копию на сохранённой ветке продолжает без prepare. Освобождённый чистый слот готовит штатно;
другую текущую ветку не переключает. Для старой записи без ветки требуется явный --branch.
--workspace выбирает рабочую копию с теми же проверками, --prompt-file добавляет задание к заметке
о месте остановки. --dry-run только показывает действия, без fetch, подготовки и запуска.

Если UUID неизвестен, запись видна в истории, но автоматический resume невозможен. Если слот удалён,
для терминальной сессии можно выделить новый под сохранённую существующую ветку; потерянные
незакоммиченные файлы так не возвращаются. Перенос chat в другой workspace пока не поддержан:
CLI сохраняет оба UUID и сообщает блокер. История провайдера должна оставаться на диске.
Без демона известны только сессии, ранее созданные или обнаруженные CLI.

## Как `sess` находит журнал

Codex по умолчанию запускается как **chat** через `superset sessions create --local`.
Для прежнего терминального запуска добавьте `--cli`; `--agent claude` остаётся терминальным.
Chat-сессии обнаруживаются через `sessions list` во всех локальных workspace, без обязательного реестра.
Закрытые chat-сессии не входят в `ls` и лимит. `last`, `wait` и `send` доступны и по их session id;
`send` автоматически возобновляет сессию с проверкой общего лимита.

```sh
paradev-agent create --workspace W --prompt-file task.md --alias task-x
paradev-agent create --workspace W --prompt-file task.md --model gpt-6.1-sol --mode read-only
paradev-agent create --cli --workspace W --prompt-file task.md --effort high
```

`--model` и `--mode` chat передаются без изменений; `--mode` задаёт права доступа
(`read-only`, `workspace-write`, `agent`, `agent-full-access` для установленного Codex).
**Superset 2.0.2 не предоставляет effort в chat CLI.** Формат `model[effort]` также отвергается
проверкой моделей Superset. Явный `--effort` для chat выдаёт ошибку до создания сессии;
опустите его для настройки пресета либо выберите `--cli`.

Chat-журнал читается через `sessions read --limit 500`, все страницы — с непрозрачным `nextBefore`.
Повторные события item заменяют сообщение, поэтому текст не дублируется. Ответы подагентов,
рассуждения и вывод инструментов не подтверждают маркер. Якорь `send` включает chat session id
и курсор события; передавайте его в `wait --after` без изменений. Ошибки хода дают код 5,
`awaiting_input` и pending approval — код 3 с `waiting` из структурированного журнала.
Ответить на pending approval через `sessions send` Superset 2.0.2 не умеет: решение принимается
в интерфейсе Superset. `send --force` здесь отправляет обычное сообщение.

При возобновлении Superset может заменить chat session id и terminal id, сохранив нативную
сессию Codex. CLI переносит алиас и keep на новые id; используйте id/anchor из нового ответа.
Реестр сохраняет `kind: chat|cli`; `resume` продолжает тот же транспорт. Старые записи без `kind`
считаются `cli`. Для chat используются `sessions close/resume`; соседние терминалы при chat close
не убираются. RSS chat отображается как 0: `sessions list` не отдаёт память процесса.

Для терминальных сессий:

1. `ps -axo pid,ppid,rss,command` — процессы `codex` и `claude`; RSS — память процесса.
2. Окружение процесса (`ps -E` минус вывод без `-E`) — `SUPERSET_TERMINAL_ID`, `SUPERSET_WORKSPACE_ID`.
3. Codex: системный `lsof -a -p PID -Fn` находит открытый процессом
   `~/.codex/sessions/YYYY/MM/DD/rollout-….jsonl` (в том числе в другом `CODEX_HOME`). Первая запись
   `session_meta` даёт `id` и `cwd`. Выбирается единственный основной rollout; журналы подагентов
   исключаются. По последнему файлу в общей папке CLI не гадает: несколько сессий в одном cwd не путаются.
4. Claude: `~/.claude/sessions/<pid>.json` даёт `sessionId`, `cwd`, `status` (busy/idle).
   Журнал — `~/.claude/projects/<cwd, всё кроме [A-Za-z0-9] → ->/<sessionId>.jsonl`; не нашёлся — поиск
   `<sessionId>.jsonl` по всем проектам (`CLAUDE_CONFIG_DIR` переопределяет `~/.claude`).
5. Состояние «ждёт разрешения/ответа» — `superset snapshot` (`agent.state = blocked`). Для Codex события
   начала и завершения хода дополняют busy/idle; working/blocked из Superset имеют приоритет.
6. Агент, у которого среди предков есть другой агент (`codex exec`, `claude -p`, подагент), — вложенный:
   отдельной сессией не считается; `ls` показывает их число и память. npm-обёртка Codex и запущенный ею
   нативный процесс считаются одной сессией. Служебные `codex app-server`/`mcp-server` не учитываются.

Разбор Codex: `response_item/message` с ролью `user` и `event_msg/user_message` подтверждают отправку;
`response_item/message` с ролью `assistant` и `event_msg/agent_message` дают ответы. Рассуждения и вывод
инструментов не считаются ответами и не подтверждают маркер. `task_complete`/`turn_complete`/`turn_aborted`
завершают ход, `event_msg/error` сообщает ошибку API (повторяемые ошибки с `will_retry` пропускаются).
Якорь Codex включает session id и номер строки, поэтому работает и у записей без uuid; передавайте
значение `.anchor` из `send --json` в `wait --after` без изменений. После смены сессии нужен новый якорь.

Разбор Claude: сообщение человека — запись `user` с текстом (не `tool_result`; длинная вставка — в обёртке
`<pasted_content id=…>`, она при сверке отбрасывается) или `attachment`
`queued_command` (если сессия была занята); ответ — текстовые блоки `assistant` вне подагентов; конец хода —
`system/turn_duration` (с `pendingBackgroundAgentCount > 0` ход не считается законченным); ошибка API —
`assistant` с `isApiErrorMessage`. Оба формата разбирает `internal/agent/journal.go`.

**Ограничения терминального режима.** Форматы журналов могут измениться. Для Codex нужен доступный `lsof` и открытый основной
rollout; без него `ls` покажет процесс без session id, `send`/`wait`/`last` сообщат об отсутствии журнала,
а `gc` оставит сессию. Эфемерные сессии Codex без rollout не поддерживаются.
Без session id Codex `close` отказывает, чтобы не потерять возможность `resume`.
Сессия вне Superset видна в `ls`, но без терминала — отправить ей нельзя. После `/clear` у процесса новый session id и новый
журнал: якорь старого `send` в нём не найдётся. `ps -E` видит только процессы текущего пользователя.
`send` сверяет начало текста (до 200 символов) среди новых записей после отправки и проверяет время.

`create` и `resume` принимают `--agent codex|claude`; остальные команды определяют агента по chat-метаданным или живому
процессу. `close` и `gc` сохраняют тип агента в реестре. Старые записи без этого поля считаются Claude,
чтобы `resume` продолжал прежнюю сессию. Менять агента сохранённой сессии при `resume` нельзя.
В терминальном режиме модель и effort передаются Superset без подстановки: опустите их для настроек пресета; для Claude
можно явно указать `--agent claude --model opus`.

## Формат плана `paradev-agent commit`

Правила проекта — `.agent-cli.json` в корне репозитория (раздел `commit`, см. ниже). Порядок работы:

1. Общий индекс рабочей копии в коммитах не участвует: чужие staged-изменения (параллельная сессия в той
   же ветке) не мешают и остаются staged. Отказ — только если в индексе уже лежит файл плана: неясно,
   какая его версия своя. В репозитории без коммитов база сравнения — пустое дерево.
2. Сухой прогон использует **временный индекс** (`GIT_INDEX_FILE`) и временное хранилище объектов.
   Следующий шаг проверяется поверх дерева предыдущего. Общая база объектов, HEAD, ветка и
   рабочий индекс остаются доступны только для чтения. Проверки: в индексе **ровно** заявленные файлы (каждый файл покрыт
   `paths`/`hunks`, каждый путь плана что-то дал), число ханков — как выбрано, нет `forbiddenPaths`,
   сообщение по `messagePattern` и `trailerPattern`.
3. `--apply` — после успешного сухого прогона каждый коммит снова собирается во временном индексе от
   текущего HEAD, `commit-tree`, и ветка сдвигается сверкой `git update-ref HEAD <новый> <ожидаемый>`.
   Если другая сессия закоммитила в эту же секунду, сверка не проходит и коммит пересобирается на новом
   HEAD (до 3 попыток) — чужой коммит не затирается. В общем индексе затем обновляются только
   закоммиченные пути. Хуки `pre-commit` и `commit-msg` (может переписать сообщение) запускаются над
   временным индексом (`GIT_INDEX_FILE`), `post-commit` — после сдвига ветки. Сбой посередине —
   сообщение со списком уже сделанных коммитов.
4. `closeChange` — после коммита элемента запускается `closeCommand` с тем же временным индексом
   (`GIT_INDEX_FILE`: его `git add` / `git rm` попадают туда), проверяется индекс, коммит `closeMessage`
   (или сообщение из вывода команды по `closeMessageFrom`).

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "paradev-agent commit plan",
  "oneOf": [
    { "$ref": "#/$defs/commits" },
    { "type": "object", "required": ["commits"], "properties": { "commits": { "$ref": "#/$defs/commits" } } }
  ],
  "$defs": {
    "commits": { "type": "array", "minItems": 1, "items": { "$ref": "#/$defs/commit" } },
    "commit": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "message": { "type": "string", "minLength": 1, "description": "Полное сообщение: заголовок, тело, подвал" },
        "paths": {
          "type": "array",
          "items": { "type": "string", "minLength": 1 },
          "description": "Файлы от корня репозитория — целиком (git add --), включая удаление; каталог — отказ"
        },
        "hunks": {
          "type": "array",
          "items": {
            "type": "object",
            "required": ["path", "include"],
            "additionalProperties": false,
            "properties": {
              "path": { "type": "string", "description": "Отслеживаемый файл, не указанный в paths" },
              "include": {
                "description": "Номера ханков из `paradev-agent commit hunks` (с 1) или маркер-подстрока / список маркеров",
                "oneOf": [
                  { "type": "array", "items": { "type": "integer", "minimum": 1 }, "minItems": 1 },
                  { "type": "string", "minLength": 1 },
                  { "type": "array", "items": { "type": "string", "minLength": 1 }, "minItems": 1 }
                ]
              }
            }
          }
        },
        "closeChange": { "type": "string", "pattern": "^[\\w./-]+$", "description": "Задача для closeCommand после этого коммита" }
      },
      "anyOf": [
        { "required": ["message", "paths"] },
        { "required": ["message", "hunks"] },
        { "required": ["closeChange"], "not": { "anyOf": [{ "required": ["paths"] }, { "required": ["hunks"] }] } }
      ]
    }
  }
}
```

Пример:

```json
[
  {
    "message": "feat(store-delivery): поле «Доставка» в политике магазина\n\nЧто получилось…\n\nCo-Authored-By: …",
    "paths": ["libs/backend/automation/src/policy.ts", "apps/web/src/app/settings/store.tsx"],
    "hunks": [{ "path": "README.md", "include": "Доставка" }]
  },
  { "closeChange": "store-delivery" }
]
```

### `.agent-cli.json`

```json
{
  "commit": {
    "forbiddenPaths": ["node_modules/**", ".env.local", "**/*.pem"],
    "messagePattern": "^(feat|fix|docs)\\([^)]+\\): \\S|^close\\((change|step)\\): \\S",
    "trailerPattern": "^Co-Authored-By: ",
    "closeCommand": "node .ai/tools/close-change.mjs {task}",
    "closeMessage": "close(change): {task}",
    "closeMessageFrom": "Сообщение коммита: (.+)",
    "closeRequires": [".ai/changes/{task}.md"]
  },
  "slot": {
    "mainBranch": "main",
    "remote": "origin",
    "localFiles": [".ai/learnings/local/rules.md", ".ai/learnings/local/context/"],
    "take": "node tools/slot.mjs --branch {branch} --from {base}",
    "release": "node tools/slot.mjs --release --from {base}",
    "prepare": [
      { "symlinkIfMissing": "node_modules" },
      { "copyIfMissing": [".env.local", "config/worker/development.json"] },
      { "run": "npx prisma generate", "ifChanged": ["prisma/"] }
    ]
  }
}
```

- `forbiddenPaths` — glob от корня: `**` — любые каталоги, `*`/`?` — внутри сегмента; шаблон без `/`
  сравнивается с именем в любом каталоге.
- `trailerPattern` проверяется у сообщений плана, не у сообщений закрытия.
- `closeMessage` или `closeMessageFrom` — одно из двух; `closeRequires` — пути, из которых хотя бы один
  должен существовать (иначе предупреждение в сухом прогоне).
- `closeCommand` и `run` разбиваются по пробелам и запускаются без оболочки.
- `slot.mainBranch` — основная ветка (по умолчанию — `origin/HEAD`, иначе `main`); `slot.remote` — `origin`.
- `slot.localFiles` — файлы и каталоги (рекурсивно), исключённые из Git, но нужные в каждом worktree; см.
  «Локальные файлы слота».
- `slot.take` / `slot.release` — своя команда проекта вместо встроенной логики (`{branch}`, `{base}`
  подставляются); запускается в слоте, ветку и подготовку делает она. agent-cli оставляет за собой имя
  воркспейса, локальные файлы и проверку живых сессий. Перед `slot.take` CLI обновляет удалённые ветки,
  после проверяет назначение и свежесть ветки. Нет ключа — встроенная логика.
- `slot.prepare` — шаги подготовки; нет ключа — шаги по умолчанию (см. «Слоты»), конфиг не нужен.

Для команд `slot` и автоматического переноса локальных файлов `.agent-cli.json` берётся **из рабочей копии
основной копии проекта** (путь — `superset projects list`), если он там есть, иначе из слота: так работает и
неотслеживаемый файл, который в worktree не попадает. Его стоит исключить локально — строкой
`/.agent-cli.json` в `$(git rev-parse --git-common-dir)/info/exclude` (общий для всех worktree), иначе он
висит в `git status` как `??`. `paradev-agent commit` читает правила из корня текущего репозитория (слота).

## Слоты

Основной workspace Paradev сохраняет свой путь при смене Git-ветки. В `agent-cli` чистая основная
копия без чужой активной работы используется для ветки текущей задачи.

Дополнительный слот выделяется через `slot take` и при нехватке создаётся штатным `slot create`.
У слота есть отдельная от основной копии папка `…/slot-N`. Свободный workspace называется `slot-N`,
назначенный — `slot-N · <задача>`, а заголовок чата может иметь вид `slot-N — <тема>`. Папка остаётся
прежней при смене ветки. `worktrees open` делает существующую копию видимой в Paradev.
Если хост отмечает регистрацию как импорт существующего worktree, команды слотов её исключают,
даже при совпадении имени и папки.

Свободный слот — без ветки (`(detached HEAD)`): так его оставляет `paradev-agent close`. Занятый — на ветке задачи.

`slot prepare` (взять слот):

1. Живая сессия в слоте обычно блокирует подготовку (`--force` — только по явному разрешению).
   Собственный чат может создать ветку в описанном ниже режиме. Основная копия проекта и ветка
   с именем выбранной базы исключены.
2. **Свежая база**: `git fetch --atomic --prune origin '+refs/heads/*:refs/remotes/origin/*'` — обновление
   удалённых веток в общем репозитории worktree с удалением устаревших tracking refs. Рабочую копию и
   локальные ветки основной копии не трогает (никаких
   checkout/reset/pull). `<base>` — `--from` (например `release-1` или `origin/release-1`), иначе
   `slot.mainBranch`, иначе `origin/HEAD`, иначе `main`. SHA базы и удалённой ветки задачи сохраняются
   для подготовки. Fetch упал или базы нет → ошибка (код 1), от старой базы не ответвляется.
   `--offline` — явно без fetch, от уже полученных remote refs.
3. Есть `slot.take` — после синхронизации локальных файлов запускается она (в слоте, с `{branch}` и
   `{base}`); шаги 4–8 не выполняются, проверка шага 9 обязательна. В выводе — её строки ✅/⚠️,
   иначе последние строки. JSON также содержит `existing`, `from`, `base` (SHA), `fetched`.
4. Текущая ветка слота не влита в `mainBranch` (локальную или `origin/…`) → отказ (код 9);
   `--allow-unmerged` — осознанно увести слот с неё (ветка остаётся в git). Слот без ветки — свободен.
5. Грязный слот → копия изменённых и неотслеживаемых файлов, `status.txt` и `diff.patch` в
   `~/.agent-cli/backups/<слот>-<время>/`, затем остановка с кодом 9. `--carry` — после копии ветка с
   переносом правок поверх.
6. Локальные файлы (см. ниже): сначала слот → основная копия, затем основная копия → слот.
7. Ветки нет — `git switch --no-track -c B <полученный SHA базы>`; есть (локально или на origin,
   например правки по ревью) — `git switch B` и fast-forward от полученного SHA `origin/B`.
   Ошибка fast-forward останавливает подготовку, локальные коммиты сохраняются. Удалённая на сервере
   ветка не восстанавливается из старого tracking ref. Отставание существующей ветки от `origin/<base>` —
   только строка «позади … на N: merge — по решению человека».
8. Шаги подготовки — `slot.prepare` или по умолчанию:
   - `symlinkIfMissing`, `copyIfMissing`, `cloneIfMissing` — из основной копии, если в слоте нет.
     Клон — `cp -c` (APFS, macOS) или `cp --reflink=always` (Linux): почти без места; не вышло или Windows —
     пропуск, установку делает следующий шаг. У клона `ready` — `{ "папка": "путь" }`: папка готова, только
     если есть этот путь (неготовая, например с одним кэшем сборки, заменяется клоном); `ifSame` — файлы,
     которые должны совпадать в слоте и основной копии, иначе клона нет;
   - `run` — команда в слоте (`cwd` — подкаталог). Без условий — всегда; с `ifChanged` (пути изменились
     между прежним HEAD слота и новым), `ifMissing` (путей нет) или `ifNoHooks` (git не находит каталог
     хуков: `git rev-parse --git-path hooks`) — если сработало хотя бы одно. `envFromMain` —
     `{ "ПЕРЕМЕННАЯ": "файл" }`: путь к файлу основной копии, если в слоте его нет (файл не читается);
   - **по умолчанию** (нет `slot.prepare`): для каждого отслеживаемого `package-lock.json` /
     `pnpm-lock.yaml` / `yarn.lock` (вложенный — только если у основной копии есть его `node_modules`) —
     клон `node_modules` при одинаковом lock-файле (npm — ещё и вложенных `node_modules` workspace-пакетов
     из `package-lock.json`; готовность — по первому обязательному пакету папки), затем установка (`npm ci`, `pnpm install --frozen-lockfile`,
     `yarn install --frozen-lockfile`) при `ifMissing` / `ifChanged`; npm — с
     `npm_config_userconfig` = `.npmrc` основной копии, если своего нет. Есть `.husky` — `npx husky`,
     `lefthook.yml` — `npx lefthook install`, оба при `ifNoHooks`.
9. Проверка фактической ветки: новая содержит полученный SHA базы, существующая — полученный SHA
   своей удалённой ветки (если та есть). Ошибка, включая устаревшую ветку после `slot.take`, → код 9,
   без переименования и автоматического сброса результата. Затем имя воркспейса →
   «slot-N · <--task или ветка>» (`superset ws update --name`).

**Новая ветка из собственного чата.** `slot prepare` и `slot_prepare` подтверждают единственный живой
чат по `SUPERSET_WORKSPACE_ID` и `SUPERSET_TERMINAL_ID` или `CODEX_THREAD_ID` среды запуска.
Аргументы `workspaceId` и `ownerSessionId` выбирают записи и сами по себе не подтверждают вызывающий чат.
После fetch нужна чистая рабочая копия с detached HEAD на SHA выбранной базы, без операции Git.
Имя ветки должно быть новым и локально, и на выбранном remote. `branchOnly: true` в результате означает
создание ветки с сохранением SHA, файлов, имени слота и резерва чата. Этот режим ограничен Git-веткой.
Хуки checkout, синхронизация локальных файлов и шаги подготовки относятся к обычной подготовке свободного слота.
Если настроен `slot.take` проекта, его подготовка требует свободного слота. Когда среда MCP не содержит
идентификаторов чата, используйте CLI из этого чата.

`--dry-run` делает fetch (он ничего не меняет в рабочих копиях и проверяет сеть и базу) и все проверки,
печатает базу, план локальных файлов и хуки; ветку, имя, файлы и бэкапы не трогает.

`slot create` (новый слот):

1. `--project` — имя или id проекта Superset. Имя — `--name` (ровно `slot-N`) или следующий свободный
   номер. Номер занят, если у проекта есть воркспейс с этим слотом (в том числе «slot-N · задача»),
   локальная ветка `slot-N` или папка `slot-N` рядом с другими worktree проекта; занятый `--name` — отказ
   (код 9).
2. Свежая база — как у `prepare` (шаг 2): `--base`, иначе `slot.mainBranch`, иначе `origin/HEAD`; fetch
   упал — ошибка до вызова Superset; `--offline` — от уже полученного `origin/<base>`.
3. `superset ws create --local --project <id> --name slot-N --branch slot-N --skip-branch-prefix
   --base-branch <base>` — без агента. Папку worktree Superset выводит из ветки, поэтому ветка временная:
   папка `…/slot-N` остаётся за слотом навсегда, какие бы ветки он потом ни брал.
4. В новом worktree — `git switch --detach <sha origin/base>` и `git branch -D slot-N`: слот свободен, как
   после `paradev-agent close`. Грязный сразу после создания (например, setup-скрипт проекта) — строка в выводе и
   код 9. Если хост вернул путь вне ожидаемого формата `…/slot-N`, смены ветки не будет.

`--dry-run` — fetch, выбор имени и команда Superset; ничего не создаёт. Сессию `create` не запускает, лимит
сессий его не касается. Дальше — обычный `slot prepare`.

`slot take --project P --branch B` — `create` и `prepare` одной командой. Свободный слот — имя ровно
«slot-N», без активного назначения и живого транспорта, чистый, HEAD влит в `mainBranch`. Слоты проверяются по номеру. Нет такого — `create` (`--from` → его `--base`), затем `prepare` нового слота с теми же
`--branch`, `--task`, `--from` и флагами. Ветка `B` уже стоит в каком-то слоте — отказ (код 9) с его именем и id.
Последняя строка вывода — `воркспейс: <id>`, в `--json` — `workspace`, `created`, `create`, `prepare`.
`--dry-run` показывает план `prepare` или `create` и массив `skipped`. Для каждого пропущенного слота
доступны `workspaceId`, `name`, `branch`, `head` и `reasons`. Например, `assigned` означает, что слот
назначен задаче, `live_session` и `native_process` указывают на работающих агентов, `reserved` означает
резерв чата, `dirty` — локальные изменения, а `unmerged` — недостижимость HEAD из проверенных
`baseRefs`. Git-данные могут быть недоступны. При `inspection_failed` проверка уже пропущенного
слота осталась неполной.

Если указан `reusePreview`, при завершённой прежней задаче можно проверить план `close` для этого
workspace. После согласованного освобождения проверьте `release.status: released` и повторите
`slot take --dry-run`. В MCP тот же процесс доступен через `slot_take` и `session_close`.

Release — внутренний шаг `paradev-agent close` после закрытия сессии. Есть hook `slot.release` — запускается он.
Иначе: грязный слот → отказ (код 9); fetch базы; незапушенные коммиты — предупреждение (они остаются в
ветке); `git switch --detach origin/<base>` — ветка свободна для другого слота. Затем локальные файлы
слота → основная копия и имя «slot-N».

### Локальные файлы слота

`slot.localFiles` — пути относительно корня репозитория: файлы и каталоги (рекурсивно; символьные ссылки
пропускаются). Переносятся **копией** (не ссылкой — загрузчики правил ссылки не читают).

- Нет в цели → копия. Одинаково → пропуск.
- Отличается → решает **база**: содержимое, на котором слот и основная копия сошлись в прошлый раз
  (хеши в `~/.agent-cli/local-files.json`, по слоту). Изменилось только в источнике → переносится;
  только в цели → цель новее, пропуск; с обеих сторон или базы ещё нет → **конфликт**: цель не меняется.
- `.md` сливаются по разделам (заголовок `#`…`######` до следующего заголовка; в блоках кода заголовки не
  считаются): новый раздел добавляется после своего предшественника, раздел, изменённый только в
  источнике, обновляется, конфликтующие разделы показываются и не перетираются, разделы только в цели
  остаются. Прочие файлы — так же, но целиком.
- Удаления не переносятся (раздел, удалённый в цели, не возвращается, пока его не изменят в источнике).
- Перед любой перезаписью прежняя версия цели копируется в
  `~/.agent-cli/backups/<слот>-local-<время>/{main|slot}/<путь>`; в отчёте — путь бэкапа.

Когда срабатывает:

| Когда | Направление | Режим |
| --- | --- | --- |
| `slot prepare` | слот → основная, затем основная → слот | применяет (`--dry-run` — план) |
| `close`, `gc --apply` — при release | слот → основная | применяет; конфликт блокирует успешное завершение |
| `slot sync-back <слот>` | слот → основная | сухой прогон, `--apply` — применить |
| `slot sync <слот>` | обе стороны | сухой прогон, `--apply` — применить |

Автоматический перенос ничего не теряет: конфликтующее не перезаписывается, перезаписанное — в бэкапе;
конфликты видны в выводе и в `localFiles.conflicts` (`--json`). Код 9 при конфликте возвращают sync-back/sync и close; результат частичного release проверяется отдельно.

`paradev-agent close` и `paradev-agent gc --apply` освобождают слот через один release и проверяют Git,
отсутствие сессий/native-процессов, перенос локальных файлов и имя slot-N. Одного переименования
недостаточно. Повторное закрытие уже свободного detached-слота не повторяет release hook.

## `gc`

По умолчанию — только проект воркспейса, из которого вызван CLI (`SUPERSET_WORKSPACE_ID` или cwd);
другие — явно `--project a,b`. Закрывает (без `--apply` — только показывает):

- сессии в состоянии idle с маркером «готово» в последнем ответе (`--done`, по умолчанию `[[DONE…]]`) или
  без изменений журнала дольше `--idle` (30m); session id — в реестр, как при `close`;
- терминалы с `exited` и агентом в состоянии `exited`; пустые шеллы — без агента, без заголовка и с
  экраном-приглашением (`terminals read`);
- панели, чей терминал не живёт в воркспейсе (иначе приложение показывает мёртвые сессии);
- освобождает слоты тем же механизмом, что close; грязные слоты и слоты с несколькими сессиями оставляет с причиной.

Никогда не закрывает: работающие, ждущие разрешения, с вопросом в последнем ответе (строка на «?»),
с пометкой keep и сессию, из которой вызван CLI.

## Активность по файлам

`paradev-agent activity FILE... --recent 30m --json` сообщает о совпадениях по работающим
сессиям в worktree и недавним упоминаниям имени файла в журналах живых сессий.
Команда возвращает `busy` с файлами, ID терминалов и причинами. Содержимое журналов остаётся
в процессе CLI. Текущая сессия исключается при совпадении workspace и terminal ID.
Проверку использует [pen-cli](https://github.com/burningyouth/pen-cli) при закрытии Pen.

## Где лежат данные

`~/.agent-cli/` (или `$AGENT_CLI_HOME`); реестр пишется атомарно, с правами 600:

- `config.json` — `maxSessions` (лимит выполняющихся сессий), `superset` (`~/.superset/bin/superset`; голое имя ищется в PATH, не
  нашлось — `~/.superset/bin/superset`, так что PATH к нему не нужен), `sendAcceptTimeoutSec` (20);
- `sessions.json` — последние состояния сессий, алиасы и `keep`; `paradev-agent forget` удаляет запись;
- `session-log.jsonl` — события истории, права 600; запись под блокировкой и fsync до обновления снимка;
  после сбоя журнал восстанавливает незаписанный снимок, неполный последний append игнорируется;
- `local-files.json` — база синхронизации локальных файлов: хеши файлов и разделов по слотам;
- `backups/` — копии грязных слотов и перезаписанных локальных файлов; автоматически не чистится.

Без `maxSessions` одновременно могут выполняться до 10 сессий. CLI и MCP читают
`~/.agent-cli/config.json`. Если задан `AGENT_CLI_HOME`, оба читают `config.json`
в этом каталоге. При использовании отдельного профиля передайте одинаковый
`AGENT_CLI_HOME` обоим процессам. Команды работают без подключения к Paradev.

Оркестратор получает оба числа одним вызовом `session_list` или `paradev-agent ls --json`.
`count` — сколько сессий выполняет работу сейчас, `limit` — настроенный лимит.

```sh
paradev-agent config get maxSessions
paradev-agent config set maxSessions 5
paradev-agent config reset maxSessions
```

При переходе со старой версии явно заданный лимит сохраняется. Профиль без
этого ключа получит новый общий лимит 10. Чтобы сохранить личный лимит 5, выполните
`config set maxSessions 5` новой версией. `reset` удаляет только этот ключ.

## `close`: закрыть сессию и освободить слот

```sh
paradev-agent close task-x --note "Проверки готовы; дальше ревью" --json
paradev-agent close --summary-file /absolute/path/outcome.md --json
paradev-agent close --result /absolute/path/result.json --json
```

Одна операция: сохранить запись для resume, закрыть сессию, выполнить штатный release проекта
или встроенный release, проверить результат. --note и --summary-file необязательны: иначе сохраняется
последний доступный ответ. Ветка задачи и история агента остаются. Ничего не коммитится и не публикуется.
Если сессия исчезла, close по записи или из пустого слота доводит release до конца.
--dry-run показывает план. Грязный слот или другая сессия блокируют действие до закрытия целевого чата.

Для собственного chat в слоте сохраняется защита доставки финального ответа: CLI копирует итог
в `~/.agent-cli/finish-jobs/<id>/summary.md`, возвращает resultFile и уникальный receipt.
Агент вызывает close последним действием и включает receipt буквально в финальный ответ.
Worker ждёт до 10 минут успешного завершения хода с этим receipt, отсутствия новых сообщений и approvals.
Нет подтверждения — чат остаётся открытым. Tool output, reasoning и ответ субагента не подтверждают доставку.
Отдельный daemon не используется. Терминальное самозакрытие использует короткоживущий worker без receipt.

Перед release worker ждёт фактического завершения chat/native-процессов до 90 секунд.
Один шаг release выполняется один раз: hook `slot.release` проекта либо встроенный механизм.
Уже detached-слот повторно через hook не освобождается. Проверяются чистота, detached HEAD,
сохранность ветки задачи, отсутствие сессий/native-процессов и имя slot-N. Конфликт локальных файлов — ошибка.
`queued` означает только очередь; `completed` — проверенное освобождение. close/release отражаются отдельно.

Prepare, resume и close используют блокировку слота и его поколение в `~/.agent-cli/slot-locks/`.
Изменение назначения отменяет отложенное самозакрытие. Блокировки слота и реестра не перехватываются
по возрасту/PID: после сбоя сначала убедитесь, что операция завершилась, затем удалите указанный lock.
После частичной ошибки прочитайте resultFile и фактическое состояние, не повторяйте release вслепую.
Старые `paradev-agent sess …`, `paradev-agent finish` и `paradev-agent slot release` — совместимые входы в тот же процесс.

## Локальный поток ответов Paradev

Используйте абсолютный путь к локальному журналу хоста `chat.db` (обычно
`~/.paradev/host/<host-id>/chat.db`) и точные ID чатов. Команда читает SQLite
в режиме read-only и проверяет только перечисленные сессии. Поддерживаются
чаты Codex и OpenCode внутри Paradev, когда их хост сохраняет общий журнал.

```sh
paradev-agent events watch SESSION_ID [ANOTHER_SESSION_ID] --journal "$journal"
paradev-agent events ack SESSION_ID 'EPOCH:SEQ' --journal "$journal"
```

`watch` пишет NDJSON в stdout и ждёт новые записи до прерывания или
`--timeout SEC`. Первый запуск воспроизводит сохранённую историю явно
выбранных чатов. Типы событий: `answer`, `question`, `permission_required`
и `error`. Ответ включает текст завершённого сообщения ассистента из
завершённого хода. Завершение хода не закрывает задачу.

Курсор уникален вместе с ID сессии в этом журнале. Сохраняйте эту пару
с результатом и подтверждайте события по очереди после обработки. После
переподключения неподтверждённое событие приходит снова с тем же курсором.
Подтверждённый курсор хранится под `AGENT_CLI_HOME/events` (по умолчанию
`~/.agent-cli/events`). Для независимых потребителей используйте разные профили.
`watch` останавливается с ошибкой, если обнаружит смену поколения или пропуск
в журнале. Удалённая история не восстанавливается.

Поток работает локально через stdout. Подключение личного ChatGPT или
пробуждение Альфреда в эти команды не входит.
